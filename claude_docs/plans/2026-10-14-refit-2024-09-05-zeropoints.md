# Handoff: refit the 2024-09-05 zeropoint epoch

**Status:** open, written 2026-10-14. Needs the raw frames of the night of
2024-09-04, which live on Tim's local machine (formerly
`/Users/tim/MMT/skycam_data/2024-09-04`, possibly on `/Volumes/Samsung_4TB`), so
do it there.

## Why

PR #13 (merge `0452293`) made `ALCOR_ZEROPOINTS` **de-blended**: the photometry
aperture (4 px, ~0.5 deg) picks up neighbouring stars, and
`alcor_calibrate_photometry` now adds a per-row blend term (`blend_*`) to the
catalog side of `ext_*`. Zeropoints fit the old way absorbed the average
neighbour light (~0.1 mag in G), so they had to be refit on de-blended
magnitudes. See the "Aperture blending" paragraph in CLAUDE.md.

Two epochs were refit or added from data on hand (2026-05-19, 2026-10-15). The
**2024-09-05** epoch could not be, because its frames were not on any mounted
volume. It was instead **shifted** by the 2026-05-19 blend-vs-no-blend
difference:

| band | old zp | old color | applied shift (zp / color) | shipped zp | shipped color |
|------|--------|-----------|----------------------------|------------|---------------|
| r    | 14.670 | -0.323    | -0.111 / +0.049            | 14.559     | -0.274        |
| g    | 15.438 | -0.023    | -0.098 / +0.022            | 15.340     | -0.001        |
| b    | 14.988 | +0.479    | -0.061 / -0.045            | 14.927     | +0.434        |

That assumes the absorbed neighbour light is a property of the catalog and the
star sample, not of the night. It is plausible but untested. This epoch governs
every frame nearer 2024-09-05 than 2026-05-19, i.e. **all of 2025-01 to
~2025-07**, so it is worth checking.

## Procedure

1. **Get current code.** `git pull` on `main` (at or after `0452293`), then
   `pip install -e ".[test]"`. Confirm that `from skycam_utils.alcor import
   alcor_blend_terms, ALCOR_BLEND_EFFICIENCY` works.

2. **Re-measure the night. Do not reuse old `*_phot.csv`.** Old CSVs have no
   `blend_*` and no frame registration, and the blend geometry assumes a
   centred aperture. Either of these works:
   ```bash
   alcor_process_night /path/to/2024-09-04 -o /tmp/zp2024 --workers 8
   # or, per frame: alcor_star_photometry <frame> -o /tmp/zp2024/<frame>_phot.csv
   ```
   Aperture-only output is fine: `zeropoint_calib.py` accepts both the plain
   and the `_ap` schema.

3. **Check registration.** Look at `frame_dx`, `frame_dy` and `frame_nreg` in
   the CSVs. This is the epoch's own fitting night, so expect a shift of ~0 px
   from ~100 stars. A shift of 1 px or more means the 2024-09-05 WCS epoch
   itself is off; stop and investigate before trusting the blend terms.

4. **Sanity-check the method by reproducing the old fit.** Run it without
   `--blend`:
   ```bash
   python claude_docs/scripts/zeropoint_calib.py 2024-09-04=/tmp/zp2024
   ```
   It should land near the OLD values (r 14.670/-0.323, g 15.438/-0.023,
   b 14.988/+0.479). For 2026-05-18 this reproduced G to 0.006 mag. A large
   miss means the inputs differ from the original fit (frame selection,
   photometry options) and the comparison below is not apples to apples.

5. **The real fit:**
   ```bash
   python claude_docs/scripts/zeropoint_calib.py --blend 2024-09-04=/tmp/zp2024
   ```
   Compare it with the SHIPPED values above. On 2026-05-18 de-blending dropped
   the G fit rms from 0.134 to 0.078 mag, so expect a similar drop here.
   - **Agreement within ~0.03 mag:** the shift hypothesis held. Still replace
     the entry with the fitted values, since they are measured.
   - **A larger difference:** the 2025-01..07 calibration was off by that much
     since PR #13. Say so in the PR.

6. **Update `skycam_utils/alcor/config.py`.** Replace the `2024-09-05` entry
   of `ALCOR_ZEROPOINTS`, and rewrite its paragraph in the comment block above
   (it currently says "NOT refit ... shifted by ..."). Also update the sentence
   in CLAUDE.md's "Aperture blending" paragraph that says the 2024-09-05 epoch
   was "shifted by May's blend-vs-no-blend difference rather than refit".

7. **Validate on nights that use this epoch.** Run
   `claude_docs/scripts/night_throughput.py` (it reads stored `ext_*`, so first
   re-measure, or recalibrate via `alcor_calibrate_photometry`) on a few clear
   2025-01..2025-06 nights, e.g. 2025-01-01, 2025-05-06, 2025-06-20. Before
   PR #13 the clear-night floor there was ~0.00. Report what it is now.

8. **Run the tests** (`pytest`), then open a PR on a topic branch (never push
   straight to `main`).

## Gotchas found on the way (so they are not rediscovered)

- **Star labels.** About 2158 catalog stars have no `NAME`; photometry labels
  them `HD <n>`. Joining on `NAME` silently drops them, so use
  `_catalog_calibration_map()` or `_alcor_star_labels()`. The script now does.
- **The script had a stale data path** (`alcor/data/`) from before the package
  split; it was removed in PR #13. If it errors on a path, that is the cause.
- **Registration matters for blending.** In 2026-10 an off-centre aperture
  (1.4 px) made the blend model over-predict by ~1/0.7. The fitted
  `ALCOR_BLEND_EFFICIENCY = 0.9` assumes registered photometry.
- **Time-dependent zeropoint.** Even refit, the epochs are a nearest-epoch step
  function over a throughput drift of ~0.1 mag/yr (the dome-soiling cycle in
  CLAUDE.md). That is a separate, open task; this refit does not address it.
